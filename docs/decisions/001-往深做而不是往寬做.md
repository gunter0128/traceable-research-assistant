# 001：往深做，而不是往寬做

日期：2026-10-14

## 背景

V0、V1 做完，V2 也部署到 AWS 上跑過一輪之後，我回頭看這個專案，覺得它還是很陽春。功能都有，但每個功能都只做到「正常情況下能動」。這種程度的 RAG 系統現在用 AI 很快就能生出來，沒辦法證明我有工程判斷力。

我用五個層次來檢查每個功能：能動 → 出錯時還是正確 → 量得到快慢、準度、成本 → 根據數字改進並說得出取捨 → 改版和出事時能維護。結果幾乎每個地方都停在第一層。最明顯的例子是 `process_document`：chunk 是一段一段 commit 的，處理到一半失敗時，前面的 chunk 不會被清掉，而 `search_similar` 又不看文件狀態，所以一份標成 failed 的文件，它的半套內容還是會出現在答案裡。正常測試完全測不出來。

## 決定

不加新功能，挑三條主線往下挖：

- **A. 文件處理管線**：修掉半套 chunk 的問題、改成背景處理、重試和冪等、S3 跟 DB 的一致性、批次 embedding。
- **C. 營運**：結構化 log、每個請求各段耗時、每次問答的成本、先寫假設再壓測找瓶頸、固定網址和 CI/CD。
- **B. 問答品質**：拒答門檻、逐句引用、評估資料集和自動評分接進 CI，用數字決定要不要採用 hybrid search、reranker 這些改法。

順序是 **A → C → B**。

## 為什麼是這個順序

B 跟論文最相關，也最有特色，照理說應該先做。但 A 有真的 bug，在會留下髒資料的管線上量問答品質，量出來的數字本身就不可信，等修完 A 還要整批重跑。C 的 log 和耗時紀錄在做 B 的實驗時也會用到，所以放在中間。

代價是 B 排在最後，時間不夠時會被壓縮。所以 A 要控制在大約一週內。

## 其他

真實使用者大概只有我自己加上研究室兩三個人，不會更多。評估資料會用他們實際問的問題，再加上用 LLM 從文件產生、經過我人工檢查的問題來補足數量。對外講的時候照實際人數講。

刻意不做的東西：Kubernetes、拆成微服務。這個規模用不到，加了只是為了履歷好看，被問「為什麼需要」的時候答不出來。
