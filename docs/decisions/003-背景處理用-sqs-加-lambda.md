# 003：文件處理改成背景執行，佇列用 SQS，worker 用 Lambda

日期：2026-10-14

## 背景

上傳 PDF 時，解析、切段、每段呼叫 OpenAI 轉向量、存進資料庫，全部都在同一個 request 裡做完才回應。小檔案沒問題，但幾百頁的 PDF 要呼叫幾百次 OpenAI，使用者要等好幾分鐘，連線很可能直接逾時。V1 時刻意先用同步的做法，現在要改掉。

改成背景處理之後，API 只負責收檔、建紀錄、丟一張工單，然後立刻回應；真正的處理交給另一個程式（worker）。這牽涉到兩個選擇：工單放哪裡，以及 worker 跑在哪裡。

## 工單放哪裡

考慮過三種：

- **FastAPI 的 BackgroundTasks**：回應之後在同一個程式裡接著處理。最簡單，但容器一重啟，處理到一半的工作就消失了，也沒有重試。這等於只是把問題藏起來。
- **拿 Postgres 當佇列**：documents 表本身就是工單，worker 定期去撈 pending 的文件。不用多一種服務，建文件和建工單也能在同一個 transaction 裡。但 worker 要一直輪詢資料庫，Neon 就沒辦法閒置休眠，免費方案的運算時數很快就會被吃完。
- **SQS**：選這個。閒置時幾乎不花錢，也不會吵醒資料庫。重試和 dead-letter queue（失敗太多次的訊息會移到另一個佇列，等人工處理）都是內建的。worker 處理到一半掛掉，訊息過一段時間會自己重新出現，不需要我自己寫這些機制。

SQS 的代價是：文件紀錄存進 Postgres 和訊息送進 SQS 是兩個系統，可能出現「紀錄存好了、訊息沒送出去」的情況，文件會永遠卡在處理中。這要另外處理。

## worker 跑在哪裡

- **再開一個 ECS service**：跟 API 完全分開，但等於多開一台 Fargate，每個月多一筆固定費用，而大部分時間它都閒著。
- **跟 API 放在同一個 Fargate task**：不用多付錢，但兩者共用 CPU 和記憶體，處理大 PDF 時會拖慢 API。
- **Lambda**：選這個。

選 Lambda 是因為這兩種工作的特性不一樣。API 要隨時待命，使用者打開就要能回應，所以放在一直開著的 Fargate。文件處理一天可能只發生幾次，量也不固定，適合有工作才啟動、按次計費的 Lambda，閒置時成本是零。這個系統入伍期間也會一直開著，成本是實際的限制。

代價是要多學一種部署方式；而且 Lambda 單次最多只能跑 15 分鐘，超大的文件之後可能要拆開處理。

## 區域

整個 AWS 目前開在雪梨（當初的規劃留下來的），但 Neon 資料庫在新加坡，使用者在台灣。API 每查一次資料庫，就要在雪梨和新加坡之間來回一趟。這只影響速度，不影響正確性，所以先不搬。Lambda 也放在雪梨，跟 S3、SQS 同一區。等主線 C 量出各段的實際耗時後，再根據數字決定整個系統要放在哪裡。
