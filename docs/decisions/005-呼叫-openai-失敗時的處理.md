# 005：呼叫 OpenAI 失敗時怎麼處理

日期：2026-10-15

## 背景

系統有三個地方會呼叫 OpenAI：文件處理時把每段 chunk 轉向量、問答時把問題轉向量、問答時生成答案。三個用同一把 key、連同一個服務，所以會遇到的問題都一樣。檢查之後發現四個問題：

1. **等太久才放棄。** OpenAI 套件預設單次等待上限是 600 秒。OpenAI 卡住時，文件處理會一直等到 Lambda 的 10 分鐘上限被強制中斷，連標失敗都來不及；問答最壞要等 10 分鐘才看到錯誤。
2. **錯誤不分種類。** 套件內建會快速重試 2 次，之後不管什麼錯都直接標失敗。但速率限制、網路斷線這種等一下就會好的錯誤，跟 API key 失效、餘額不足這種等多久都不會好的錯誤，應該分開處理。
3. **一段一段呼叫。** 300 頁的文件要依序呼叫 330 次，但 embedding API 一次就能送很多段。
4. **Lambda 冷啟動時上網下載 tiktoken 的編碼表。** 拖慢啟動，而且下載網址連不上時 Lambda 會完全無法啟動。

## 決定

### 錯誤分兩類

- **暫時性**：網路斷線、超時、速率限制、OpenAI 伺服器錯誤。等一下再試通常會好。
- **永久性**：API key 無效、沒有權限、餘額不足、請求格式錯誤。立刻停，不重試，訊息寫「系統設定有誤，請聯絡管理員」，因為這需要人來處理。

有一個陷阱：OpenAI 的「餘額不足」跟「速率限制」回的都是 429，套件會把它當成暫時性錯誤一直重試。所以要看錯誤內容裡的代碼（`insufficient_quota`）把它挑出來，當成永久性。

分類寫在 `core/openai_client.py`，三個呼叫點共用；分類之後怎麼處理，由 `document_service` 和 `qa_service` 各自決定。

### 處理方式看「誰在等」

**問答**（使用者盯著畫面）：使用者最多等 **1 分鐘**就要看到結果或錯誤。每次呼叫最多等 15 秒、重試 1 次，轉向量和生成答案兩次呼叫加起來，最壞情況大約 1 分鐘。還是失敗就回 503「AI 服務暫時無法使用，請稍後再試」，不再像現在一樣回 500。

**文件處理**（背景執行）：OpenAI 出問題時，最多自動重試約 **10 分鐘**才放棄。

```
第 1 次處理：每次呼叫最多等 30 秒，失敗就隔 0.5、1、2、4 秒重試，共 4 次（秒級）
            還是不行 → 文件維持「處理中」，叫 SQS 2 分鐘後再把工單送回來
第 2 次處理：同上
第 3 次處理：同上，還是不行 → 標失敗「AI 服務暫時無法使用，已自動重試 3 次，請稍後按重試」
```

本機沒有 SQS，延後不了，秒級重試撐不過去就直接標失敗。

### 考慮過、沒選的做法

- **秒級重試撐不過去就直接標失敗，讓使用者手動重試。** 最簡單，但 OpenAI 停擺 10 分鐘，這段時間上傳的文件全部要一份一份手動重試。
- **交給每小時的掃描晚點重送。** 原本我推薦這個，因為完全重用 A2 做好的機制，不用新增東西。但使用者上傳文件通常就是準備要問問題，OpenAI 恢復之後還要再等 30～90 分鐘文件才準備好，體驗很差。改成讓 SQS 2 分鐘後重送，代價是 worker 多一個 `sqs:ChangeMessageVisibility` 權限，程式也多一些。每小時的掃描還是保留，負責 Lambda 整個當掉的情況。

### 其他

- **批次送**：一次送 100 段轉向量，300 頁的文件從 330 次呼叫降到 4 次。上限是 2048 段，100 段已經能把次數降到百分之一，單次請求也不會太大。
- **tiktoken 編碼表在 build image 時先下載好**，執行時不用上網。

## 這些數字怎麼來的

30 秒、15 秒、4 次、1 次、2 分鐘都是推算出來的起始值，不是量出來的。依據是：正常的 embedding 呼叫不到 1 秒、生成答案幾秒，等待上限要比正常值大很多，才不會誤判；重試間隔每次加倍，4 次加起來大約 7.5 秒，能撐過網路閃斷；問答的總等待時間由「使用者最多等 1 分鐘」倒推回來。主線 C 開始記錄每次呼叫的實際耗時和重試次數之後，再根據數字調整。
