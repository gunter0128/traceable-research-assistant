# 006：S3 跟資料庫的一致性

日期：2026-10-15

## 背景

上傳和刪除文件都會同時動到兩個系統：S3 放檔案，Neon 放紀錄。資料庫的 transaction 管不到 S3，所以「兩邊都成功、或兩邊都不做」做不到，一定有可能只成功一邊。

只成功一邊會留下兩種不一致，嚴重程度差很多：

- **孤兒檔案**：S3 有檔案，資料庫沒紀錄。使用者看不到，功能也不會壞，只是多佔一點空間。
- **壞掉的紀錄**：資料庫有紀錄，S3 沒檔案。使用者看得到這份文件，但它再也處理不了、也重試不了。

原本上傳是先存 S3 再建紀錄，失敗只會留下孤兒檔案，還好；但刪除是先刪 S3 再刪紀錄，失敗會留下壞掉的紀錄。另外發現刪 workspace 時，資料庫會連帶刪掉文件紀錄，但完全沒有程式碼去刪 S3 上的檔案，每刪一個有文件的 workspace 就留下一批孤兒檔案。

## 決定

**原則：寧可留下孤兒檔案，也不要留下壞掉的紀錄，再定期把孤兒檔案清掉。**

- **上傳**：順序不變（先 S3 再紀錄）。建紀錄失敗時，順手把剛存的檔案刪掉。
- **刪除文件**：順序反過來，先刪紀錄、再刪檔案。刪檔案失敗也不影響刪除成功，只留下孤兒檔案。
- **刪除 workspace**：先記下底下所有文件的檔案位置，刪掉紀錄後再一個一個刪檔案。
- **對帳**：每小時的 sweeper 跑完卡住文件的重送後，比對 S3 上 `documents/` 底下的檔案和資料庫的紀錄，刪掉沒有紀錄、而且放超過 1 天的檔案。

「順手刪掉」本身也可能失敗（剛好斷線），所以對帳是最後的保險，不管孤兒檔案是怎麼來的都會被清掉。

### 為什麼要放超過 1 天才刪

上傳是先存 S3 再建紀錄。對帳剛好在這兩步之間執行的話，會看到一個「還沒有紀錄」的新檔案，不加這個條件會把正在上傳的檔案誤刪。1 天遠大於上傳需要的時間。

### 為什麼放在 sweeper 裡

考慮過三種：不清（檔案累積，以目前用量費用幾乎是零）、另外建一個每天跑的 Lambda、放進每小時的 sweeper。選最後一個：sweeper 本來就每小時叫醒一次資料庫，多查一欄不會增加 Neon 的消耗，也不用多維護一個 Lambda。對帳放在重送後面，對帳出錯也不影響比較重要的重送。

代價是 worker 的 Role 要多兩個權限：列出 bucket 裡的檔案（限定 `documents/` 前綴）和刪除 `documents/` 底下的檔案。兩個 Lambda 共用同一個 Role，所以處理工單的 worker 也拿到了刪除權限，這是當初選擇共用 Role 時接受的代價。

## 業界的說法

這種「沒辦法包在同一個 transaction 裡，就決定失敗時留下哪一種不一致，再用補救動作和定期對帳收尾」的做法，跟跨服務交易常講的 saga（每一步失敗有對應的補救動作）和 reconciliation（定期比對兩邊、修正差異）是同一套想法，只是這裡的規模小很多。
