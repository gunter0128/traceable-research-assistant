# 008：用心跳偵測處理中斷，自己寫 OpenAI 的重試

日期：2026-10-15

## 背景

007 加了 15 分鐘的處理期限，解決了「程式在次數 +1 之前就當掉，文件永遠卡在處理中」。但使用者要面對一段完全沒有資訊、也不能做任何事的 15 分鐘。

根本原因是系統分不出「還在處理」和「已經當掉」：畫面上的「處理中」可能是在排隊、正在處理、等下一回合重試，或是 Lambda 早就死了，四種看起來一模一樣。當掉的程式不會留下任何訊號，系統只能保守地等到「不可能還在正常處理」才敢判定出事。

討論時又發現兩個現在就存在的問題：

- OpenAI 遇到速率限制時，回應可能附上「請等 N 秒」（Retry-After），openai 套件會照做，最多等 120 秒。文件處理一次呼叫最壞可能 8 分鐘沒有任何動靜；問答重試那 1 次，最壞也要等超過 2 分鐘，「最多等 1 分鐘」其實不成立。
- 問答要呼叫 OpenAI 兩次，各自的上限都沒違反，加起來還是可能超過 1 分鐘。

重試是套件在 `embeddings.create()` 那一行裡面自己做的，我們插不上手：沒辦法在重試之間做事，也沒辦法限制最多等多久。

## 決定

### 1. 自己寫 OpenAI 的重試

把套件的重試關掉（`max_retries=0`），改成自己的迴圈。每一次嘗試之前、要等多久、總共還剩多少時間，都由我們決定。等待的間隔照業界常見的 exponential backoff with jitter：0.5、1、2、4 秒每次加倍，再乘上一點隨機（避免大家同一時間一起重試）；OpenAI 有說「請等 N 秒」就照它的，但有上限。

| | 文件處理 | 問答 |
|---|---|---|
| 每次嘗試最多等 | 30 秒 | 15 秒 |
| 最多試幾次 | 5 次 | 2 次 |
| OpenAI 叫我們等 N 秒 | 照做，但最多等 60 秒 | 5 秒以內照做；超過就直接放棄，告訴使用者稍後再試 |
| 總時間 | — | 整個問答（轉向量 + 生成）共用 60 秒的預算，剩下的時間不夠就放棄 |
| 每次嘗試前 | 報平安（見下面的心跳） | — |

60 秒的預算就是之前決定的「問答最多等 1 分鐘」，從估算變成程式保證。5 秒是體驗上的判斷：等幾秒算「有點慢」，等三四十秒使用者就會以為壞了，不如直接讓他知道。這些數字都是起始值，主線 C 有了 OpenAI 實際回應的數據再調。

### 2. 心跳 + 租約：讓活著的程式一直報平安

文件多一個狀態「處理中（processing）」，跟「排隊中（uploaded）」分開：

```
uploaded    排隊中 / 等下一回合重試   還沒有 Lambda 在處理
processing  處理中                    某個 Lambda 拿到了租約，正在處理
processed   完成
failed      失敗
```

Lambda 開始處理時，要先**取得租約**：在 documents 表上記一個只有它知道的隨機代碼（claim_token）和「最後報平安的時間」（heartbeat_at）。處理過程中每做一步就報一次平安（更新 heartbeat_at 和進度）。

判定規則：

- **處理中，超過 5 分鐘沒報平安** → 程式死了 → 標「處理中斷，請按重試」
- **排隊中，送出工單超過 15 分鐘還沒有人開始處理** → 標「處理逾時，請按重試」（007 的規則，只剩這個用途）

5 分鐘要比「正常情況下最長多久沒報平安」長。自己寫重試之後，每次嘗試前都會報平安，最長的空檔是一次嘗試 30 秒加一次等待最多 60 秒，約 1.5 分鐘；回合之間的休息狀態是「排隊中」，不算在這條規則裡。

排隊中維持 15 分鐘，是因為排隊本來就可能很久：同時最多 2 個 Lambda，一次上傳很多份時後面的要等前面的；等下一回合重試也在這個狀態。每次延後到下一回合時，15 分鐘重新計算（等於重新排隊），不然 OpenAI 一直叫我們等的極端情況下，第 3 回合還沒開始就會被誤判逾時。

被判定中斷時，租約一起收回（清掉代碼）。那個其實只是很慢的 Lambda 之後再來報平安，會發現代碼對不上而自己放棄，不會把已經標成中斷的文件又「救活」，讓使用者看到狀態跳來跳去。

### 3. 鎖：租約本身就是鎖

原本打算另外加一個鎖，防止同一份文件被兩個 Lambda 同時處理。寫的時候發現**租約本身就能當鎖**：

- **取得租約**是一個有條件的更新：只有在「不是處理中」或「處理中但已經 5 分鐘沒報平安（前一個死了）」時才會成功。兩個 Lambda 同時搶，資料庫保證只有一個會成功，另一個直接跳過這張工單。
- **報平安和最後存結果時，都要對得上自己的代碼。** 如果對不上，代表自己被判定死掉、文件已經交給別人了（例如自己其實只是很慢，使用者按了重試），就放棄這次處理、整批 rollback，不會跟新的那個 Lambda 存出兩份內容。業界把這種代碼叫 fencing token。

選這個做法而不是資料庫的 advisory lock，是因為 advisory lock 綁在資料庫連線上，連線池會讓它很難推理；租約存在表裡，看得到、測得到，而且跟心跳是同一份資料，不會兩套機制對不起來。

心跳要在「整份文件一個 transaction」之外**另外寫入並立刻 commit**，不然要等到處理完才看得到，就沒有意義了。所以報平安用另一條獨立的資料庫連線。

### 4. 進度

記錄「已處理幾段 / 總共幾段」，報平安時一起更新，前端顯示「處理中 200 / 330」。

### 5. 問答的體驗

- 失敗時把問題放回輸入框，不用重打
- 等待時顯示「思考中…」
- 資料庫出錯時回 503「服務暫時無法使用，請稍後再試」，不再是「request failed with status 500」。用 FastAPI 的全域錯誤處理，所有 API 一起套用

## 做完之後

| 情況 | 現在 | 之後 |
|---|---|---|
| 正常處理 | 「處理中」 | 「處理中 200 / 330」 |
| OpenAI 暫時出問題 | 約 10 分鐘內有結果 | 一樣 |
| OpenAI 叫我們等很久 | 文件處理可能被套件拖住 8 分鐘；問答可能等超過 2 分鐘 | 文件處理每次最多等 60 秒；問答保證 60 秒內有結果 |
| Lambda 處理到一半當掉 | 乾等 15 分鐘 | 約 5 分鐘顯示「處理中斷，請按重試」 |
| 其實沒死只是很慢，使用者按了重試 | 可能存出兩份內容 | 租約對不上的那個自動放棄 |

## 代價

- 程式複雜度明顯增加：自己的重試迴圈、獨立的報平安連線、租約的條件更新。
- 新增欄位，要跑一次 migration。
- 「5 分鐘」「15 分鐘」「60 秒」「5 秒」都是推算的起始值。
- OpenAI 每次都叫我們等滿 60 秒的極端情況下，一回合最壞約 6.5 分鐘（5 次嘗試 × 30 秒 + 4 次等待 × 60 秒），3 回合加起來會超過 005 說的「約 10 分鐘」。一般的暫時性錯誤（連不上、伺服器錯誤）不受影響，演練 1 實測 8.6 分鐘。
- 報平安跟主要的處理同時在改同一份文件：處理時寫入 chunk 會對文件加 `FOR KEY SHARE` 鎖，報平安更新一般欄位加的是 `FOR NO KEY UPDATE`，PostgreSQL 裡這兩種不衝突，不會互相卡住。
