# 009：任何會讓使用者等待的地方，都要讓他能取消

日期：2026-10-16

## 背景

A 主線做完後回頭看，所有的設計都在想「系統怎麼自己處理好」：自動重試、心跳、期限。但使用者在等待的時候只能等，沒辦法做任何決定。他可能發現傳錯檔案、不需要這個答案了，或者寧願晚點再自己重試。

自動重試是系統在幫使用者，但決定權應該還是在使用者手上。

## 會讓使用者等待的地方

| 地方 | 最久等多久 | 改之前 |
|---|---|---|
| 問答 | 60 秒 | 只能等 |
| 文件排隊中 / 處理中 / 等下一回合 | 約 5～15 分鐘 | 只能等，或整份刪掉 |
| 上傳 | 約 3 秒 | 太短，不需要 |

## 決定

### 文件處理：「取消處理」按鈕

排隊中、處理中的文件可以取消，狀態變成「已取消（cancelled）」，文件和檔案都留著，之後可以按重試，或直接刪掉。跟刪除的差別是：刪除是整份不要了；取消是先停下來，等一下再說。

做法是直接用 008 的租約：取消 = 把狀態改成已取消，同時清掉租約代碼。

- 正在處理的 Lambda，下次報平安或要存結果時代碼對不上，會自己停下來、寫到一半的全部丟掉
- 還在排隊的，Lambda 拿到工單時搶不到租約（不是排隊中了），直接跳過

所以不用另外設計「怎麼通知一個正在跑的 Lambda 停下來」，worker 的程式完全不用改。租約把「通知」變成了「檢查」：不去聯絡正在跑的程式（很難），只改資料庫裡的代碼，讓它下次自己發現（簡單、可靠）。

判斷能不能取消，交給資料庫的有條件更新（`UPDATE ... WHERE status IN ('uploaded', 'processing')`），不寫成「先查狀態、再改」。先查再改的話，查和改之間 Lambda 可能剛好處理完，就會把已經完成的文件誤標成已取消（check-then-act 競爭）。

### 問答：「思考中…」旁邊的「取消」按鈕

用瀏覽器內建的 AbortController 中斷請求，把問題放回輸入框，不跳錯誤提示。

這只是**前端停止等待**：後端已經送出的 OpenAI 請求收不回來，會在背景跑完，這次的費用還是會花掉。要讓後端也真的停下來，得偵測前端斷線再中斷 OpenAI 的請求，複雜很多；一次問答最多 60 秒、費用不到 0.01 美元，不值得。

## 代價

- 文件多一個狀態「已取消」，前端、重試、API 都要認得它
- 問答的取消不會省到錢
