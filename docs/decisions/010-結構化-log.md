# 010：結構化 log

日期：2026-10-16

## 背景

A 主線做完之後，系統會自己重試、延後、判定中斷，但這些事發生的時候我完全看不到。CloudWatch 裡只有 uvicorn 的一行行請求紀錄和 Lambda 的 START / END，我們自己的程式一筆 log 都沒寫。

實際遇到的問題：
- 演練時想知道「文件在第幾批轉向量的時候失敗、OpenAI 重試了幾次」，只能看資料庫最後的狀態去猜
- 處理時間從 4.2 秒變 7.2 秒，不知道多出來的 3 秒花在哪
- 處理時發生預料之外的錯誤，使用者看到「處理時發生錯誤」，但錯誤的細節沒有留在任何地方

## 決定

### 每一筆 log 是一行 JSON，API 和 Lambda 共用同一份程式碼

```
{"time": "...", "level": "INFO", "event": "embed_batch", "request_id": "d1501fa4cc72", "document_id": 42, "batch": 1, "chunks": 100, "duration_ms": 812}
 └──────────── 每一筆都有的固定欄位 ────────────────────────────────────────────┘ └──── 這種事件自己的欄位 ────┘
```

JSON 的好處是 CloudWatch Logs Insights 可以直接用欄位查詢和統計，例如「document_id = 42 的所有紀錄」、「過去一天 embed_batch 平均花多久」。純文字只能用關鍵字搜。

用 Python 內建的 logging 加上自己寫的格式（`app/core/log.py`，大約 30 行），不用 AWS Lambda Powertools：Powertools 主要為 Lambda 設計，API 那邊用起來彆扭，而且我想清楚知道每一行在做什麼。

### 用請求編號把 API 和 Lambda 串起來

一份文件的處理會經過 API → SQS → Lambda，三個地方是分開的程式。每個 HTTP 請求產生一個隨機的 `request_id`，放進送給 SQS 的工單裡，Lambda 處理時沿用它：

```
API     uploaded / dispatched        request_id = d1501fa4cc72
           │ 工單：{"document_id": 42, "request_id": "d1501fa4cc72"}
           ▼
Lambda  claimed / embed_batch / processed   request_id = d1501fa4cc72
```

`request_id` 也放在 API 回應的 `X-Request-ID` header，使用者回報問題時可以用它查。

編號用 ContextVar 存，在請求 / 工單一開始設好，之後寫的每一筆 log 自動帶上，不用每個函式都把編號傳來傳去。Lambda 會重複用同一個程式處理下一張工單，所以每張工單開始時兩個編號都要重設，不然會帶到上一張的。

### 記哪些事件

> 2026-11-09 更新：下表是 [046](046-簡化上雲後的可靠性機制.md) 整理後、程式現在真的會寫的事件（B4 對過程式碼）。拿掉的：`cancelled`（取消拿掉了）、`deferred`（不再自動延後）、`heartbeat`、`embed_batch`、`parsed`（每一步的計時拿掉了）、`openai_retry`（改用 SDK 的重試）、`db_probe`（測量模式換成健康檢查）；`s3_upload` 更早就沒了（013 改成瀏覽器直接傳到 S3 時，換成 `upload_started`）。`qa_failed` 的 `error_type` 從 `temporary`／`permanent` 改成錯誤的類別名稱，跟 `failed` 一樣。告警用到的事件有測試檢查程式還在寫（tests/test_alarms.py）。

| 地方 | 事件 |
|---|---|
| API 每個請求 | `request`：方法、路徑、狀態碼、花多久、使用者編號；沒接住的錯誤（500）是 ERROR、附錯誤堆疊 |
| 上傳 / 重試 | `upload_started`（發上傳許可，記檔案大小）、`uploaded`、`dispatched`（`mode` = `queue` 送工單 / `inline` 本機直接處理）、`dispatch_failed`（ERROR）、`retry_requested` |
| Lambda 拿到工單 | `message_received`：Lambda 的執行編號、這張工單第幾次被拿出來；`message_skipped`（文件已經刪掉）；`message_crashed`（ERROR，附錯誤堆疊） |
| 處理文件 | `claimed`（第幾次處理）/ `claim_skipped`（文件現在的狀態，被刪掉是 `deleted`）、`downloaded`、`chunked`、`processed`（整份花多久 `total_ms`）/ `failed`（給使用者的原因、`error_type`）/ `lease_lost`（`status`、`total_ms`）、`unexpected_error`（ERROR，附錯誤堆疊） |
| OpenAI 重試 | 只有文件處理會重試，由 SDK 自己寫一筆 INFO，event 是一句英文 `Retrying request in 0.500000 seconds (retry 1 of 2)`（`app/core/log.py` 把它接成同樣的 JSON，也帶文件編號） |
| 用量 | `openai_usage`（用途、模型、token 數、`cost_usd`）、`quota_exceeded`（`scope` = `user` / `system`） |
| 問答 | `qa_embed`、`qa_search`、`qa_generate`（各自的 `duration_ms`）、`qa_failed`（`error_type` = 錯誤的類別名稱） |
| 定期掃描 | `sweep`（`duration_ms`）、`expired_overdue`、`sweep_crashed`（ERROR） |

API 請求、問答的每一步、定期掃描都記 `duration_ms`；文件處理只記整份的 `total_ms`（046 之前每一步都記，B2-1 拿掉了）。問答的 `qa_search` 要留著：曾經量到一次搜尋卡了 88 秒（docs/refactor/FOLLOW_UPS.md）。

uvicorn 自己的請求紀錄關掉（`--no-access-log`），由我們的 `request` 事件取代，不然同一個請求會有兩筆、兩種格式。

### 不記使用者的內容

只記長度，不記內容：問題記字數、文件記檔案大小和字數，檔名也不記。研究室的文件和問題可能是還沒發表的研究，log 不受權限控制、誰能看 CloudWatch 誰就看得到，不該變成另一個存使用者資料的地方。

除錯時真的需要內容，用 `document_id` 去資料庫查，那裡有權限控制。

### log 保留 30 天

CloudWatch 預設永久保留，會一直累積費用。30 天夠查最近的問題；更長期的趨勢之後用指標記錄（指標比 log 小很多）。7 天太短，入伍期間出了問題，回來可能已經查不到了。

## 代價

- 每一份文件處理會多寫十幾筆 log，量很小，費用可以忽略
- 只記長度的話，遇到「某個問題答得很奇怪」這種問題，沒辦法單靠 log 重現，要請使用者提供問題
- 錯誤堆疊裡可能出現程式內部的資訊，但不會有使用者的內容（我們丟出的錯誤訊息裡沒有放內容）

## 第一個發現

本機測一份很小的文件（1 段），總共 1.8 秒，其中報平安 3 次就花了 1.4 秒（第一次 978 ms，因為要新開到新加坡資料庫的連線，之後每次約 210 ms）。報平安的成本比預期高很多，C2 用真的大文件確認。
