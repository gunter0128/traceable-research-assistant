# 013：固定網址，API 改用 Lambda，前端上雲

日期：2026-10-17

## 背景

C4 原本只是「每次部署 IP 都會變，很麻煩」，仔細看才發現問題更多：

| 問題 | 影響 |
|---|---|
| 每次部署 IP 都會變 | 每次都要去主控台查新 IP |
| 前端沒有部署在任何地方 | 只有我的電腦能開，研究室的同學完全用不了 |
| 連線沒有加密（HTTP） | 登入的密碼、登入後的 token 都是明文在網路上傳 |
| 測試只能用 `/docs` 頁面 | 不是給一般使用者用的 |

目標：**一個固定的 HTTPS 網址，打開就是前端畫面，前端再呼叫同一個網址底下的 API。**

## 我當時的疑問

### 為什麼 ECS 沒有固定網址？

ECS 只負責「把容器跑起來」，不負責「外面的人怎麼找到它」。每次部署新版本、容器當掉被換掉、從 0 調回 1，都是一台新的機器，就有新的 IP。要有固定入口，得在前面另外加一個負載平衡器（ALB），它會追蹤現在活著的容器是哪個，把請求轉過去。Fargate 的容器也不能直接綁固定 IP。

Lambda 本來就是「被請求叫醒」的服務，入口是它的一部分：開啟 Function URL 之後，AWS 維護一個固定的網址，後面的 Lambda 怎麼開怎麼關，網址都不會變。

### API 不是應該全年常開的嗎？改成 Lambda 會怎麼運作？

要分清楚「隨時都能用」和「隨時都在跑」：

| | ECS | Lambda |
|---|---|---|
| 隨時都能用（網址任何時候都會回應） | ✅ | ✅ |
| 隨時都在跑（有一台機器一直開著等請求） | ✅ | ❌ 有請求時才開 |

Lambda 的 API 一樣全年都能用。沒有開著的 Lambda 時，請求進來 AWS 當場開一個（冷啟動，多等幾秒）；處理完會留著一段時間，期間的請求都很快；閒置一陣子才被收掉。兩個人同時用，AWS 會同時開兩個。

這跟 worker 現在的運作方式一模一樣：worker 被 SQS 叫醒、sweeper 被排程叫醒、API 被瀏覽器的請求叫醒，三個都是同一種東西。

### 為什麼前端跟後端是同一個網址？

CloudFront 有一張「路徑 → 轉給誰」的對照表（behavior）：`/auth/*`、`/workspaces*`、`/documents/*`、`/usage/*` 轉給 API 的 Lambda，其他全部轉給放前端檔案的 S3。瀏覽器從頭到尾只跟 CloudFront 講話。

這跟本機開發時 `vite.config.ts` 的 proxy 是同一個意思。同一個網址就不會遇到 CORS（瀏覽器不讓網頁呼叫不同網址的 API，除非 API 明確允許），前端程式也完全不用改，本機和雲端都是呼叫 `/auth/login`。

## 考慮過的選項

| | A. ECS + ALB | B. API 改成 Lambda |
|---|---|---|
| 每月費用 | 約 45～50 美元（ALB、容器、公有 IP），沒人用也要付 | 約 0～1 美元，有請求才算錢 |
| 我當兵 4 個月 | 約 200 美元 | 幾乎不花錢 |
| 要改的程式 | 幾乎不用 | 上傳要改成瀏覽器直接傳到 S3 |
| 速度 | 一直開著，每次都快 | 閒置後第一個請求多等幾秒 |

## 決定

**選 B。** 這個系統的特性是使用者很少（2～3 個人），而且要在我當兵期間一直開著。A 每個月 45 美元，絕大部分是在付沒人用的時間。

這不是「Lambda 比 ECS 好」：使用者很多、隨時都有人在用的時候，Lambda 幾乎一直是熱的，按請求計費可能反而比較貴，冷啟動也會影響比較多人，那時 ECS + ALB 比較適合。是**以這個系統的使用量，Lambda 比較划算**。

### 整體架構

```
                    CloudFront（固定 HTTPS 網址）
                    ┌──────────┴──────────┐
              網頁畫面                    API 請求
                 │                          │
           S3（前端檔案）            Lambda：API（有請求才跑）
                                            │
               使用者的瀏覽器 ──直接上傳──→ S3（PDF）
                                            │
                                    SQS → Lambda：worker
                                            │
                                    Neon 資料庫（新加坡）
```

整條線上沒有任何一台需要一直開著的機器。

### 上傳改成瀏覽器直接傳到 S3

Lambda 一次最多收 6 MB 的請求，我們的上限是 20 MB，所以檔案不能再經過 API。改成三步：

1. 前端跟 API 要「上傳許可」（`POST /workspaces/{id}/uploads`）：API 檢查是不是 PDF、大小、今天的用量，用自己的權限預先簽好一張許可（presigned POST）
2. 瀏覽器拿許可把檔案直接傳到 S3
3. 前端告訴 API「傳好了」（`POST /workspaces/{id}/documents`）：API 確認檔案真的在 S3 上，才建紀錄、交出去處理

許可裡寫死了「只能存到這個位置、檔案大小在 20 MB 以內、10 分鐘內有效」，條件由 S3 自己檢查，就算有人改了前端程式也繞不過去。

這也是業界處理大檔案上傳的標準做法：檔案不經過 API，API 不用一次吞下 20 MB。

幾個安全上的細節：
- S3 的 key 是 `documents/<workspace 編號>/<隨機碼>.pdf`。第 3 步只接受發給這個 workspace 的 key，不然有人拿到別人的 key，就能把別人的檔案「認領」到自己的 workspace 讀內容
- 同一個 key 只能建一筆紀錄：兩筆紀錄指向同一個檔案的話，刪掉其中一筆，另一筆的檔案也跟著不見
- key 裡不放檔名：檔名可能透露研究內容（010），檔名只存在資料庫
- 順序還是「先有 S3 的檔案、再建紀錄」（006）：傳了卻沒說「傳好了」，只會留下沒人用的檔案，每小時的對帳會清掉

### 問答的時間預算從 60 秒改成 50 秒

CloudFront 等後端回應最多 60 秒（要更久得另外申請），超過就直接回錯誤給使用者。Lambda 冷啟動還要再加幾秒，所以留 10 秒的餘裕。

### API 的 Function URL 設成公開

Function URL 有兩種：公開（任何人都能呼叫）、或要 AWS 簽名才能呼叫。原本想設成只有 CloudFront 能呼叫，但這種設定下，**POST 請求要由瀏覽器自己算好內容的雜湊值**放在 header 裡，前端要多做很多事。

所以設成公開。代價是有人知道 Lambda 的網址的話，可以繞過 CloudFront 直接呼叫。但 API 本身有自己的登入檢查（JWT），Function URL 也是 HTTPS，繞過 CloudFront 不會多得到什麼權限。

### 不買網域

先用 CloudFront 給的網址（`https://xxxx.cloudfront.net`），免費、有 HTTPS，只是不好記。之後隨時可以加，不影響現在的設計。

### ECS 不用了

驗證沒問題之後，ECS 的 service、cluster、防火牆規則都刪掉。在 ECS 上部署的經驗還是留在 `docs/deployment-commands.md`。

## 代價

- 閒置一陣子後的第一個請求要多等幾秒（冷啟動）
- 上傳流程變複雜：從一個請求變成三步，前端也要跟著改
- 問答的時間預算少了 10 秒
- 多了一個要管的東西（CloudFront），前端更新後要讓 CloudFront 的快取失效，使用者才看得到新版
