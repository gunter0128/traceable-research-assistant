# 015：告警、帳單上限、運作紀錄

日期：2026-10-19

## 背景

我入伍之後，系統要自己跑半年，期間我只有放假時能處理問題。做這個系統的目的是練習開發、部署、維護，求職時能說「我有一個跑了半年的系統」，最好能拿出證據。

到 C5 為止，系統出問題只有兩種方式會被發現：使用者跟我說，或我自己去翻 log。A 主線做的重試、延後、判定卡住，處理的是「等一下就會好」或「只影響一份文件」的問題；但有些事系統自己處理不了，一定要人處理，例如 OpenAI 的 key 失效。另外，之前討論「sweeper 壞了怎麼辦」時發現：sweeper 壞掉會在 log 寫一筆 ERROR，但沒有人在看，沒有人會知道。

## 決定

做三件事，設定全部寫在 `deploy/setup_monitoring.py`，執行一次就建好，可以重複執行。

### 1. 告警：只抓一定要人處理的事

| 告警 | 代表 |
|---|---|
| ERROR 等級的 log、Lambda 逾時 | 可能有 bug |
| OpenAI 永久性錯誤 | key 失效或餘額用完，AI 功能全部停了 |
| 全系統用量到上限 | 所有人當天都不能用了，可能有人在濫用 |
| sweeper 3 小時沒有成功巡邏 | 巡邏壞了，卡住的文件會累積 |
| DLQ 裡有工單 | 有文件連續 3 次處理到一半就死掉，系統放棄了 |

告警只在狀態改變時寄信（正常 → 告警、告警 → 恢復正常），問題持續一整週也只會收到一封，不會塞爆信箱。因為我沒辦法馬上處理，告警的意義是「放假時看信箱，就知道這段時間出過什麼事、該修什麼」。

沒有用 Lambda 內建的錯誤次數：worker 遇到 OpenAI 暫時連不上時會故意丟出 `RetryLater`（讓工單 2 分鐘後重來），Lambda 會把它算成錯誤，正常的延後也會觸發告警。改成看我們自己的 log 等級，只有真的沒預料到的事才是 ERROR。但 Lambda 超過時間上限被強制停掉時，程式沒機會寫 log，所以另外抓 Lambda 自己印的 `Task timed out`。

### 2. 帳單上限

沒人看著的半年，帳單不能失控。用 AWS Budgets 設每月 5 美元，實際超過、或預測這個月會超過，就寄信。正常一個月不到 1 美元，超過 5 美元一定是有東西不對。

OpenAI 那邊已經有程式裡的每日上限（全系統 5 美元，decisions/012），不另外在 OpenAI 網站上設。

### 3. 運作紀錄

**儀表板**：CloudWatch 上一個頁面，每天的請求數、處理的文件（成功 / 失敗）、回答的問題、OpenAI 花費、平均處理時間、錯誤次數、告警狀態。

log 只保留 30 天（decisions/010），所以儀表板不能直接查 log。先用 metric filter 把 log 轉成數字（例如「今天處理了 12 份文件」），CloudWatch 的數字保留 15 個月，半年後還看得到整段運作紀錄。數字從建好的那一刻開始累積，之前的不會補。

**維運紀錄**（`docs/operations-log.md`）：每次出事記一筆：怎麼發現、影響、原因、處理、之後怎麼避免。上線前這幾天發生過的事也補進去了。

## 代價

- 費用：metric filter 本身不用錢；自訂的數字剛好 10 個、告警 5 個、儀表板 1 個，都在 CloudWatch 的永久免費額度內（10 個數字、10 個告警、3 個儀表板）。之後再加的話就會開始收費，一個數字或一個告警每月約 0.1～0.3 美元
- ERROR 告警和 OpenAI 永久性錯誤告警會有重疊（問答時的永久性錯誤也是 ERROR），同一件事可能收到兩封信
- 告警的 email 要先點確認信裡的連結才會生效
- 告警設定不在 CI/CD 裡，改了 `setup_monitoring.py` 要自己再執行一次
