# 026：擴大評估用的知識庫

日期：2026-10-23

## 背景

跟 OpenAI 現成服務比較時（025）發現，評估用的知識庫太小：青嶼科技只有 18 份文件、38 段，OpenAI 的服務每次撈很多段，幾乎等於全部看過一遍，所以「檢索完整」是 100%。這樣的考題量不出檢索方法的差別。

接下來要做的規劃器（先分析問題要查哪些證據，再分別搜尋，來自我論文的方法）就是在改善檢索。做之前，知識庫要先大到「每次只看得到一小部分」。

學校的知識庫也一起擴大，而且要在做規劃器**之前**完成：等規劃器做完才擴大的話，我已經知道規劃器擅長和不擅長什麼，寫考題時很難不受影響。先定好考題，考題才是真的沒看過。

## 決定

### 規模

| | 原本 | 擴大後 |
|---|---|---|
| 青嶼科技 | 18 份 | 78 份（加 60 份） |
| 澄溪國小 | 8 份 | 41 份（加 33 份） |

### 加哪些文件

照「一個真實的組織會有哪些文件」來列，不是照題目來列。新文件分三類：

| 類型 | 例子 | 規則 |
|---|---|---|
| **無關的** | 採購、門禁、訪客、會議室、資安事件通報；學校的圖書館、交通車、防災演練 | 不能回答任何一題 |
| **相關但不適用的** | 2024 年版員工手冊、子公司「青嶼雲端服務」的員工手冊和出差規定、2022 年版差旅辦法、2027 年才生效的住宿費公告、還在徵詢意見的福利草案、沒有通過的加班餐費提案；學校 111、113、114 學年度的舊版要點、116 學年度的收費預告 | 不能改變任何一題的正確答案，但粗心的人可能會答錯，這是規模變大之後真實會遇到的陷阱 |
| **刻意不做的** | 把現行規定再講一遍的文件，例如「特休常見問答」 | 會讓「該引用哪份文件」變得不明確，評估就不準了 |

所有新文件都不能碰「沒有答案」那幾題的主題（年終獎金、員工宿舍、尾牙、員工認股、試用期滿調薪、台中的停車位；學校的婚假天數、營養午餐的價錢、校外教學的地點），這些題目要維持沒有答案。

### 怎麼產生

- **改寫（12 份）**：舊版、子公司、還沒生效的公告，從現有的文件逐字替換數字和適用範圍。每一處替換都要在原文剛好出現一次，不然程式就停下來。除了刻意改的地方，內容跟原文一模一樣
- **起草（81 份）**：先寫好每份文件的大綱，包括一定要出現的數字、不能碰的主題、格式和長度，再交給 gpt-4o 寫成像真的文件
- 干擾文件裡的數字都先寫進規則表（`rules.py`），題目的「不能說」用規則表算，數字有唯一的來源

清單在 `eval/<corpus>/catalog.py`，產生和靜態檢查的程式是 `eval/expand_docs.py`。

### 四道品質檢查

| 檢查 | 做法 | 結果 |
|---|---|---|
| **1. 靜態檢查** | 大綱要求的字有沒有出現、有沒有碰到禁止的主題、企業文件有沒有冒出第 7 個部門、日期有沒有超過「現在」、格式對不對 | 修了 1 份格式（學校 S-32 用了編號清單）；其餘標記逐條確認都是大綱本來就要求的內容 |
| **2. 逐份閱讀** | 81 份起草的文件全部讀過 | 修了 7 份：HR-11（設備應該歸還資訊部，不是行政部）、GEN-16（名片不歸法務組管）、GEN-18（自己多寫了一條公務車，跟「只有台北有公務車」矛盾，也可能被當成台中停車位那題的答案）、S-12（經費來源前後矛盾）、S-16（出缺席資料歸學務處）、S-19（集合地點跟流程不一致）、S-26（多了一張空白的修正紀錄表） |
| **3. 衝突檢查** | 每一題用向量找出新文件裡最相關的 6 段，請 gpt-4o 判斷有沒有改變答案（`eval/review_docs.py`） | 企業標記 8 個、學校 15 個，逐條判斷：只有 HR-22 會議紀錄要改（它寫了業務部遠距改成 2 日，等於多了一個答案來源，又沒寫生效日），其他是刻意放的舊版陷阱、舊版裡沒有修改的條文，或是誤報 |
| **4. PDF 解析** | 轉成 PDF 後用系統的解析程式讀回來 | 313 個關鍵字全部讀得到，沒有殘留的康熙部首 |

### 題目只補「不能說」

衝突檢查會寫出「粗心的人可能怎麼答錯」，例如把子公司的特休天數、2027 年才生效的住宿上限當成答案。這些補進題目的「不能說」：企業 26 題、學校 11 題。**題目和標準答案都不改**，所以擴大前後問的是同一套題目。

## 擴大後的新基準（各跑 2 輪，回答都用 gpt-4o）

| 題目 | | 我們的系統 | OpenAI file search |
|---|---|---|---|
| 企業練習題（41 題） | 全對 | 71% / 63% | 73% / 71% |
| | 檢索完整 | 65% | 86% / 89% |
| 企業考試題（17 題） | 全對 | 71% / 71% | 59% / 65% |
| | 檢索完整 | 87% | 93% / 87% |
| 學校（21 題） | 全對 | 90% / 76% | 71% / 71% |
| | 檢索完整 | 94% | 100% |
| 平均回答時間 | | 1.7～1.8 秒 | 4.5～5.1 秒 |

擴大前我們的系統在練習題是 80% / 80%、檢索完整 81%；擴大後掉到 71% / 63%、檢索完整 65%。答錯的題目大多是「該用的文件沒搜到」。考題確實變難了，而且難在檢索。

兩邊各有強項：

- **OpenAI 的檢索比較好**：檢索完整高出 20 個百分點左右。它每次撈的段落多，而且同時用關鍵字和語意搜尋、搜完再排序
- **我們的回答比較好**：考試題高約 9 個百分點、學校題高約 12 個百分點，差距一樣在「列出各種情況、不適用也要說」（019）
- **我們快將近 3 倍**

所以接下來的規劃器有很明確的目標：**把檢索完整拉近 OpenAI 的水準，同時保住回答的優勢**。

## 代價

- 新文件還是同一套流程產生的，寫法可能比真實文件整齊、相近
- 舊版文件保留了沒有修改的條文，跟真實情況一樣，但系統如果引用了舊版裡內容相同的條文，「引用完整」會算錯
- 衝突檢查只看每一題最相關的 6 段，排在後面的段落如果有問題，可能沒被檢查到
- 起草的文件有人工修正過，重新起草不會得到一樣的內容。以 repo 裡的 `.md` 為準
- 78 份、41 份還是比真實的組織小
- 擴大後的分數跟擴大前的不能直接比，要重新跑基準
