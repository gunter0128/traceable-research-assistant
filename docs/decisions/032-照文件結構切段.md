# 032：照文件結構切段（支線，線上不換）

日期：2026-10-24

## 背景

在勞動法規上量「完美的規劃器」時（031）發現：長文件上，找到那部法規不代表找到答案的那一條。例如問特休，系統找到勞基法第 38 條的後半段，卻沒找到前半段的天數表——第 38 條比 500 個 token 長，被固定長度的切法切成兩半。

這是在主線（判斷規劃器值不值得做 MLOps）之外的支線，記錄下來，不再往下做。

## 做法

`app/core/chunker.py` 的 `chunk_structured`：一層一層找文件本身的結構，先照最大的結構切，切出來還太長的那一塊再用下一層切：

章、編 → 節 → 條、點 → 一、或 1. → （一） → 句號 → 硬切

- 認的是常見的編號寫法，不是特定文件的格式；完全沒有結構的文字會退到句號，最後才硬切
- 被拆開的長條文，每一塊開頭附上位置，例如【勞動基準法 > 第 四 章 工作時間、休息、休假 > 第 38 條】
- 相鄰的完整小條文會合在一起；被拆開的條文只跟自己合併，不會變成「上一條 + 這一條的前半」
- 上限跟固定切一樣是 500 個 token

## 結果（練習題，各 2 輪）

指標的意思：

- **全對**：重點全提到、沒說錯、該拒答的有拒答
- **檢索完整**：只看有沒有找到該用的文件。青嶼科技的文件很短，可靠；勞動法規的文件很長，會高估
- **原文平均找到幾成**（勞動法規）：每題附的依據原文找到幾成，再取平均。比「全部找到才算」寬鬆、比「找到一段就算」嚴格

| | 青嶼科技 48 題 | | | 勞動法規 46 題 | | |
|---|---|---|---|---|---|---|
| | 全對 | 檢索完整 | 送給模型的 token | 全對 | 原文平均找到幾成 | 送給模型的 token |
| 固定切 5 段 | 69% / 75% | 73% | 2,114 | 74% / 72% | 58% | 2,490 |
| 照結構切 5 段 | 75% / 77% | 80% | 1,784 | 74% / 67% | 74% | 1,666 |
| 照結構切 8 段 | 75% / 75% | 80% | 2,722 | 72% / 78% | 82% | 2,717 |

照結構切的段落比較小（勞動法規平均 317 個 token，固定切 488 個），所以同樣 5 段送給模型的字比較少；8 段跟固定切 5 段的量差不多。

**檢索明顯變好、兩套方向一致；答案只小幅變好（照結構切 8 段，兩套各多 2～3 分），在隨機波動內。**

逐題看勞動法規（固定切 5 段對照結構切 8 段）：

| 題目分組 | 題數 | 固定切答對 | 照結構切答對 |
|---|---|---|---|
| 照結構切才找到全部原文 | 15 | 57% | 90% |
| 兩種都找到全部原文 | 14 | 86% | 82% |
| 兩種都沒找到全部原文 | 10 | 60% | 30% |

找到原文的題目確實變對了，但有一部分被抵銷：固定切的段落大，常常順便帶到隔壁的條文（例如「準用第 16 條」的第 15 條和第 16 條剛好在同一段），照結構切比較精準，找不到全部的時候，連順便帶到的資訊也沒了。

## 決定

- **線上維持固定長度切段**（`chunker.STRATEGY = "fixed"`）。答案的進步還不確定，而且換切法要把所有已經上傳的文件重新切段、重新轉向量
- 程式留著，評估可以用 `--chunker structured` 切換
- 不再往下做（例如「附上前後段」）。回到主線：判斷規劃器值不值得訓練成自己的模型

## 代價

- 只在練習題上比過，考試題和澄溪國小沒有確認
- 「什麼算標題」是參考三套規章類文件列的，論文、說明書這類文件沒有驗證
