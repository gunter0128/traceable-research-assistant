# 045：地端版用 docker-compose 打包

日期：2026-10-30

## 背景

044 驗收完，地端版的設定定版了（第 1 版 adapter + 相連段落合併、temperature 0）。但現在還沒有一套員工打開網頁就能用的地端版：vLLM 在實驗室手動開，考試時在筆電上把資料庫、評估程式和實驗室的模型臨時湊起來。

目標：在公司的一台 GPU 主機上，一個指令就把整套系統開起來：網頁、API、資料庫、檔案儲存、兩個模型。

## 決定

### 一、vLLM 也放進 docker-compose

兩個服務：回答（Qwen3.5-9B + 第 1 版 adapter）、轉向量（Qwen3-Embedding-0.6B）。模型檔放在主機硬碟上，掛進容器讀，不包進 image（約 19GB，每次改程式重 build 會很慢）。

| | 放進 docker-compose（選這個） | 不放，另外手動開 |
|---|---|---|
| 啟動 | 一個指令全部起來 | 網頁、API、資料庫一個指令，vLLM 另外開 |
| 需要 | 主機裝 NVIDIA Container Toolkit（讓容器用顯示卡，要管理員權限） | 不用另外裝 |
| 交給公司 | 真的一個指令 | 還要教怎麼開 vLLM |

主機沒有 NVIDIA Container Toolkit 的話，同一個設定檔可以不開 vLLM、改連已經在跑的服務（實驗室暫時用這個方式）。

### 二、檔案存在自己架的 S3 相容儲存：SeaweedFS

上傳的 PDF 在公開展示版存 AWS 的 S3，地端版不能用。改存在主機上自己架、跟 S3 用同一套 API 的儲存服務：

| | S3 相容的儲存（選這個） | 直接存主機硬碟 |
|---|---|---|
| 程式要改多少 | 只加「S3 網址」的設定；上傳（瀏覽器直傳、上傳許可）、下載、刪除、對帳都不用改 | 上傳流程要重寫，下載、刪除、對帳也要改 |
| 兩個版本 | 同一份程式，只是連到不同的儲存 | 存檔的程式兩套 |

原本選 MinIO（最常見的 S3 相容儲存），寫設定時才發現它從 2025 年 10 月起不再提供免費版的 image，只給原始碼，之後也不會再修安全漏洞。改用 SeaweedFS（開源、Apache 2.0、一個指令就能起來）；上傳用的「瀏覽器拿許可直接上傳」（POST policy）官方列了支援，但近期有人回報特定權限設定下會失敗，所以先在筆電上試，不通就換 Garage（官方相容表明確列了支援）。兩個都不用改程式，只換 docker-compose 的設定。

瀏覽器連不到容器網路裡的儲存服務，上傳許可的網址換成網頁底下的路徑（`/storage`），由 nginx 轉過去。許可的簽名只簽表單的條件、沒有簽網址，換掉網址不影響檢查。

代價是多一個服務、多一組帳號密碼。

**試過**：在筆電上用 SeaweedFS 4.48 走完整條流程（拿上傳許可 → 瀏覽器直接上傳 → 處理 → 問答），上傳回 204，不用換 Garage。

### 三、背景處理先用本機模式

沒有設定 SQS 時，上傳完直接在同一個請求裡處理（003 留下來的本機模式），不用另外架佇列。公開展示版用 SQS，是因為 Lambda 一次最多跑 15 分鐘、處理也要花錢；地端版轉向量用顯示卡，考試時 78 份文件建知識庫只花約 20 秒。

先用最大的 PDF（300 頁）量處理時間。太慢的話，再加一個定時查資料庫、處理排隊中文件的背景程式，用 008 的租約確保同一份文件只有一個程式在處理，不用另外架佇列服務。

**量過**：300 頁的 PDF（318 段）處理 8.7 秒（筆電上跑，轉向量透過 SSH 通道用實驗室的顯示卡），遠低於 nginx 等待的上限（10 分鐘），所以不加佇列。

### 四、只開給主機自己

服務只聽主機本身（127.0.0.1），從外面用 SSH 通道看，跟現在連實驗室的 vLLM 一樣：實驗室是共用的機器，系統也還沒有 HTTPS。部署到公司時，改設定檔裡對外的埠，公司內網的人就能連。

### 做法

先在筆電上跑同一份設定檔（不開 vLLM，透過 SSH 通道連實驗室的模型），把網頁、API、資料庫、儲存服務、上傳到問答整條流程測通，再搬到實驗室接上 vLLM。筆電上改完馬上能試，也不會在除錯期間佔用共用的機器。

## 結果

| | 處理 3 段的文件 | 處理 300 頁（318 段） | 問答 |
|---|---|---|---|
| 筆電（模型透過 SSH 通道用實驗室的） | 2.5 秒 | 8.7 秒 | 5.7 秒 |
| 實驗室（docker-compose，模型在同一台） | 0.5 秒 | 5.0 秒 | 3.4 秒 |

兩邊都從網頁的網址（nginx）走完整條流程：註冊 → 上傳 → 處理 → 問答，答案跟驗收時一樣。

目前是第一階段：docker-compose 開資料庫、儲存、API、網頁，模型是主機上手動開的兩個 vLLM（API 透過 `host.docker.internal` 連過去）。

**第二階段（模型也由 docker-compose 開）先暫停**：

- NVIDIA Container Toolkit 已經裝好（1.20.1），測試容器看得到 RTX 3090
- 但下載 vLLM 的 image（解壓後約 20GB）把主機的硬碟用完了：這台共用主機的系統硬碟 1TB 本來就用了九成多，資料庫寫不進檔案、一直重開，網站停了幾分鐘。刪掉 image 之後恢復（剩約 22GB），資料都在
- 要做第二階段，得先跟管理的人確認能不能把 Docker 的資料放到另一顆硬碟。在那之前，主機重開機後要手動開兩個模型
- 教訓：下載大的 image 之前，先確認剩餘空間；共用主機上也不要清整個 Docker 的快取（`docker builder prune` 會清到別人的）

## 代價

- 本機模式上傳大檔案要等處理完才回應
- 沒有每小時的 sweeper：卡住的文件在使用者查看時當場判定（007、008）還是有效，但儲存服務上的孤兒檔案不會自動清
- vLLM 的 image 很大，主機第一次啟動要下載很久
- 實驗室能不能裝 NVIDIA Container Toolkit 還不知道；不能的話，實驗室上的就不是真正的「一個指令」

## 第一階段怎麼啟動（2026-11-10 補）

第二階段暫停之後，實驗室的主機重開機要先手動開兩個模型、再開 docker-compose，步驟和參數都要記得。改成 `onprem/start.sh` 一個指令：

| 決定 | 做法 | 理由 |
|---|---|---|
| 模型怎麼跑 | 用主機上裝好的 vLLM（`.env` 的 `VLLM_BIN`），`nohup` 丟到背景，log 寫進 `onprem/logs/` | 不用下載 20GB 的 image、不用管理員權限，也不用另外裝 tmux |
| 順序 | 轉向量 → 等 `/health` → 回答 → 等 `/health` → `docker compose up -d` → 經過 nginx 打 `/auth/me` 等到 401 | 兩個模型同時開會搶顯示卡記憶體（跟 `--profile gpu` 的 `depends_on` 一樣） |
| 模型已經在跑 | 跳過，不重開 | 顯示卡是共用的 |
| 參數 | 寫在 start.sh，`tests/test_onprem_start.py` 逐一跟 docker-compose.yml 的 `vllm-embed`、`vllm-answer` 比對（包括 `VLLM_USE_FLASHINFER_SAMPLER=0`，036） | 之後換成 `--profile gpu`，模型的行為不變 |
| 避免下載 | `HF_HUB_OFFLINE=1` | 找不到模型檔就直接報錯，不會在共用主機上下載十幾 GB |
| 關掉 | `stop.sh`：`docker compose stop`（資料留著）；模型只關 start.sh 開的（記了編號，關之前確認那個編號還是 vLLM），別人開的不碰；`--keep-models` 只關網頁那些 | 共用主機上不會關到別人的東西 |
| 主機上的路徑 | `.env` 的 `VLLM_BIN`、`MODELS_DIR`、`ADAPTERS_DIR` | 換機器只改設定 |

**試過**：在 Linux（WSL 的 Ubuntu 24.04，在只有自己 loopback 的網路裡）用假的 vllm、docker 跑 22 項情境，全部通過：沒有 `.env` 或缺設定會停下來、說是哪一個；先開轉向量再開回答；環境變數對（`HF_HOME`、`HF_HUB_OFFLINE`、FlashInfer 的設定只給回答模型、`.env` 的密碼不會傳給模型）；adapter 換成主機的路徑；再跑一次會跳過已經在跑的模型；回答模型開不起來會印出 log 的最後幾行、不往下開網頁；stop.sh 只關自己開的；編號被別的程式用了不會關錯。實驗室上還沒真的跑過。

**代價**：還不是開機自動啟動，重開機後要打一次 `./start.sh`；主機上的 vLLM 要另外裝好（交給公司時要說明）。等 Docker 的資料能放到另一顆硬碟，就換成 `--profile gpu`，start.sh 可以拿掉。
