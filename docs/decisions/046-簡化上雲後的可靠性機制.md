# 046：Cloud Core：簡化上雲後的可靠性機制

日期：2026-11-09

## 背景

上雲之後，為了「OpenAI 或 Lambda 出問題時系統自己處理好」，陸續加了自動延後重試（005）、處理期限（007）、心跳與租約、自己寫的重試迴圈（008）、執行中取消（009）。每一個單獨看都有道理，疊在一起之後：

- `process_document()` 107 行，有 10 個 except、13 個離開點
- 看懂「轉向量呼叫一次 OpenAI」，要追 `_with_retries` 和 4 個 helper，中間還有 callback 從底層呼叫回來報平安
- 交易從刪除舊 chunk 開始，一路開著跨過所有 OpenAI 呼叫；報平安和記用量只好另外開 session

雲端架構和功能本身不複雜，複雜的是這些機制的連鎖：

- 心跳 → 要在重試之間報平安 → 自己寫重試 → callback → 另開 session
- 自動延後 → 錯誤分暫時／永久兩類 → 例外從 service 穿到 worker → 改 SQS 工單的可見時間 → 次數上限

目標：保留完整的雲端架構和功能，把機制降到「自己讀得懂、改得動、Debug 得了」，同時不犧牲資料正確性和公開服務的安全。

## 決定

### 一、保留

| | 為什麼 |
|---|---|
| API、Worker、Sweeper 三個 Lambda；S3、SQS、EventBridge | 雲端架構本身不是複雜的來源 |
| PostgreSQL + pgvector、OpenAI、RAG 問答（搜尋、相連段落合併、逐句引用） | 核心功能 |
| Sweeper 的逾時檢查和孤兒檔清理 | 上傳「先 S3 後資料庫」、刪除「先資料庫後 S3」（006），要靠對帳收尾 |
| 查看文件時順便檢查逾時 | 地端版沒有 Sweeper，這是地端唯一的卡住偵測 |
| Claim token + 有條件的 UPDATE | SQS 只保證「至少送一次」、使用者可能連按兩次重試：同一份文件只能有一個 worker 處理，失去處理權的 worker 不能把結果寫進去 |
| chunks 和「處理完成」在同一個 transaction | 搜尋只看處理完成的文件，不能出現「完成了，但 chunk 只有一半」 |
| SHA-256 重複文件偵測（022） | 實際發生過：重複的文件佔滿搜尋名額，答案變差 |
| JWT、Secrets Manager、每人／全系統的每日上限、用量立刻寫入、必要的告警 | 公開服務的安全和費用防護 |
| 資料庫的欄位 | 暫時不改 schema、不加 migration；不再使用的欄位先留著 |

### 二、簡化或移除

| 機制 | 改成 | 階段 |
|---|---|---|
| 自動延後重試（005）：OpenAI、S3 暫時故障時文件回到排隊中，SQS 2 分鐘後再送，最多 3 回合 | 秒級重試之後還是失敗，就標失敗，使用者按重試 | B1 |
| 心跳（008）：每次呼叫 OpenAI 之前（包括重試）都報平安 | 只在解析切段完、每轉完一批報一次；雲端、地端共用；超過 10 分鐘沒報平安才判定中斷（見「三」） | B2-1 |
| 心跳過期時由另一個 worker 接手 | 不接手：只有排隊中的文件搶得到租約，逾時標失敗，使用者按重試 | B2-2 |
| 次數上限（處理 3 次就不再處理） | 移除：不接手之後，次數只在取得租約時 +1、按重試又歸零，最多就是 1，上限永遠擋不到。「會讓程式當掉的文件被一直重做」改由前一點擋：SQS 重送的工單碰到處理中的文件直接跳過；工單本身重送 3 次後進 DLQ（有告警）。`attempts` 欄位留著，只寫進 log | B2-2 |
| 處理進度（200 / 330） | 不再寫入（B2-1）；API、前端的欄位拿掉，處理中只顯示「處理中」（B2-3）。資料表的兩個欄位留著不用 | B2-1、B2-3 |
| 文件處理的取消（009） | 移除 API、service、repository 和前端按鈕；不想等的文件直接刪掉。以前取消的文件照常顯示「已取消」、可以重試。問答的取消保留（只是前端停止等待，沒有後端的程式） | B2-3 |
| 交易的範圍 | 下載 PDF、呼叫 OpenAI 的期間不持有資料庫交易，chunks 最後才和「完成」一起寫進去 | B2-1 |
| 自己寫的重試迴圈（008） | OpenAI SDK 內建的重試 + 明確的等待上限：文件處理的轉向量每次最多等 30 秒、一共試 3 次（B3-1）。問答不自動重試（B3-2）。`_with_retries` 本身 B3-3 拿掉 | B3-1、B3-2、B3-3 |
| 錯誤分成暫時性／永久性兩類 | 收斂，告警改看狀態碼 | B3 |
| callback：`on_attempt`、文件處理的 `on_usage` | `on_attempt` 拿掉；`embed_texts` 直接回傳（向量, 用量） | B2-1 |
| callback：問答的 `on_usage` | `embed_query`、`generate_answer` 直接回傳（結果, 用量） | B3-2 |
| 問答的 `deadline`（一路傳進 `openai_client` 和重試迴圈） | 50 秒的預算保留，改成 qa_service 自己算一次：生成答案最多等「ANSWER_TIMEOUT 和剩下的時間，取小的」（見「三」） | B3-2 |
| 量資料庫連線速度的 probe（011）、處理流程裡每一步的計時 | 移除；CI 的熱身改成簡單的 `SELECT 1` 健康檢查 | B4 |

### 三、實作前要先確認的事

- **心跳（B2-1，已決定）**：比較過三種做法：

  | | 只看開始處理的時間 | 雲端看開始時間、地端留心跳 | 雲端、地端共用簡化的心跳（選這個） |
  |---|---|---|---|
  | 雲端會不會誤判 | 不會，但要靠「Lambda 的 timeout（600 秒）小於期限」這個跟 AWS 設定的約定 | 同左 | 不會，跟 AWS 設定無關 |
  | 地端會不會誤判 | 會：地端沒有強制停止，整份處理超過期限、又有人查看列表，就會被標中斷，很慢的大文件可能永遠處理不完 | 不會 | 只有「單一步驟」超過 10 分鐘才會 |
  | 程式 | 最少 | 最多：處理和逾時判斷都要分模式 | 多一個 repo 函式，每批呼叫一次 |

  以前的心跳複雜，不是因為「記最後一次有進度的時間」，而是因為每次呼叫 OpenAI 之前（包括重試）都要報平安，才逼出自己寫的重試、callback、另開 session 的 `_Lease`、`LeaseLost` 例外。改成每轉完一批報一次，這些都不需要了。

  10 分鐘怎麼來的：兩次報平安之間最長的正常空檔是「一批轉向量加上它所有的重試」，有測試擋著（改重試設定時忘了調期限會失敗）。B2-1 時是自己寫的重試，5 次 × 30 秒 + 4 次等待 × 最多 60 秒 = 390 秒（6.5 分鐘）；B3-1 改用 SDK 內建的重試之後是 3 次 × 30 秒 + 2 次等待 × 最多 120 秒 = 330 秒（5.5 分鐘），見下面「轉向量改用 SDK 內建的重試」。這兩個數字都是「假設每次請求在 30 秒內結束」的估算，不是保證（原因見本段最後）。下載加解析另外算一段：300 頁塞滿文字的 PDF（254 萬字、794 段）在筆電上解析 3.1 秒，Lambda 慢幾倍也在 1 分鐘以內。這不是絕對保證：例如回應的資料一直慢慢傳，每次都剛好不到 30 秒的等待上限，一批還是可能更久；被誤判時最後存結果會被擋下來，代價是白做一次、文件顯示中斷，資料不會錯。
- **用量和交易（B2-1）**：每轉完一批，另開一個 session 寫用量、馬上 commit，跟主 session 完全分開：後面失敗、主 session rollback，已經花掉的錢照樣有紀錄；chunks 不在那個 session 裡，不會被帶出去（而且寫用量的時候 chunks 還沒加進任何 session）。
- **資料庫交易（B2-1）**：取得租約、讀資料、查重複、報平安各自是很短的交易，做完馬上結束；下載 PDF、呼叫 OpenAI 的時候主 session 不持有交易（有測試檢查）；最後 chunks 和「完成」在同一個交易裡 commit。
- **轉向量改用 SDK 內建的重試（B3-1）**：`embed_texts` 只剩「呼叫 SDK → 錯誤翻譯成暫時性／永久性 → 照 index 排好向量、回傳用量」。用假的網路跑真的 SDK（openai 3.15.0）確認過它的規則：

  | | SDK 內建的重試 |
  |---|---|
  | 會重試的錯誤 | 連不上、超時、408、409、429、5xx；OpenAI 在 header 說要不要重試（`x-should-retry`）的話照它的 |
  | 不重試 | 400、401、403、404 這類，馬上丟出來 |
  | 重試前等多久 | OpenAI 說「請等 N 秒」：120 秒以內照做，超過就不重試、直接丟錯誤；沒說：0.5、1 秒（再乘上 0.75～1 的隨機數） |
  | 我們能設定的 | 每次請求的等待上限（30 秒）、重試幾次（2 次）。120 秒是 SDK 寫死的，設定不了 |

  重試 2 次（一共 3 次）的原因：
  - 這是 SDK 預設的次數。
  - 用同樣的假設估算，一批 330 秒，比原本估的 390 秒還短，10 分鐘的期限不用改。這不是保證：30 秒只限制連線和每一次讀取，不限制整個請求，回應一直慢慢傳的話一批還是可能更久。所以期限先維持 10 分鐘，部署後在 AWS 上量實際的間隔（docs/refactor/FOLLOW_UPS.md）。
  - 改成 3 次是 480 秒，還在期限內；4 次是 630 秒，會超過。
  - B1 之後暫時故障本來就是「標失敗、使用者按重試」，多試幾次只多擋得住很短的瞬斷。

  錯誤分類（`_classify`、`OpenAITemporaryError`、`OpenAIPermanentError`）照舊保留：document_service 靠它決定給使用者看的訊息，worker 的告警看 `error_type = "OpenAIPermanentError"`。

  餘額不足和速率限制都是 429，SDK 分不出來，所以會先重試 2 次（多等約 1.5 秒），最後還是歸類成永久性錯誤，告警照樣觸發。

  以前每次重試都寫一筆我們自己的 `openai_retry`（WARNING）；改成 SDK 寫的 INFO「Retrying request in 0.5 seconds (retry 1 of 2)」，`app/core/log.py` 把 SDK 的 logger 接到同樣的 JSON 格式，CloudWatch 一樣查得到。
- **問答的時間預算（B3-2）**：問答不重試之後，原本的 `deadline` 主要是用來「重試前檢查還剩多少時間」，已經用不到。但 50 秒的上限不能直接拿掉：

  | | 轉向量 | 搜尋 | 生成答案 | 加起來 | 外面的上限 |
  |---|---|---|---|---|---|
  | 雲端 | 15 秒 | 資料庫，平常幾十毫秒 | 15 秒 | 約 30 秒 | CloudFront、API Lambda 都是 60 秒；冷啟動約 3.4 秒（新部署後第一次 14 秒） |
  | 地端 | 15 秒 | 同上 | 45 秒（本機的模型比較慢，037） | 約 60 秒 | nginx 600 秒；但 037 定的是「整個問答 50 秒」 |

  雲端加起來本來就在 50 秒內，預算只有資料庫異常地慢（超過 20 秒）時才會起作用；地端加起來會超過 50 秒，要靠預算擋住。所以保留 `ANSWER_BUDGET_SECONDS`，但寫法改成 qa_service 裡一個減法：從轉向量開始算，生成答案最多等 `min(ANSWER_TIMEOUT, 剩下的時間)`；剩不到 1 秒就不送出去，直接回 503。`openai_client` 不再知道預算的存在，只收一個 timeout。

  跟其他等待上限一樣，15、45 秒是連線和每一次讀取的上限，不是整個請求的總時間；資料庫的查詢本身也沒有等待上限（改之前也沒有）。所以 50 秒是設計上的目標，不是嚴格保證。

  用量：`embed_query`、`generate_answer` 直接回傳（結果, 用量），qa_service 一拿到就放進清單，最後在 `finally` 一起寫進資料庫（時機跟改之前一樣：中途 commit 會讓查出來的段落失效）。行為跟改之前相同，改的是傳遞方式：以前靠 `on_usage` callback 從 `openai_client` 裡面呼叫回來，現在看回傳值就知道。改之前 callback 在轉向量一成功就把用量放進清單，所以「轉向量成功、搜尋失敗」本來就記得到；改成回傳值之後，為了維持這一點，線上問答自己分兩步呼叫（轉向量 → `search_passages`），不經過 `retrieve()`。`retrieve()` 留給 train/make_answers.py，介面不變。
- **健康檢查（B4）**：拿掉 probe 時，不能換成完全沒有檢查作用的空事件，保留一個 `SELECT 1`。

### 四、分階段

一次只改一種機制，每個階段的測試和驗證分開，出問題時才知道是哪一步造成的。重構前的基準見 [docs/refactor/A0_BASELINE.md](../refactor/A0_BASELINE.md)。

| 階段 | 內容 | 狀態 |
|---|---|---|
| B1 | 移除自動延後重試 | 完成（次數上限保留：SQS 重送、接手死掉的 Lambda 仍會讓次數增加，B2 再評估） |
| B2-1 | 交易的範圍、文件處理的用量改成回傳值、心跳改成每批一次、不再寫進度 | 完成（還沒驗證的風險見 [docs/refactor/FOLLOW_UPS.md](../refactor/FOLLOW_UPS.md)） |
| B2-2 | 不接手、拿掉次數上限；手動重試改成有條件的更新（連按兩次不會把處理中的文件改回排隊中）；處理到一半文件被刪掉時正常結束 | 完成 |
| B2-3 | 取消、進度的 API 和前端 | 完成 |
| B3-1 | 文件處理的轉向量改用 SDK 內建的重試（錯誤分類、問答的 `_with_retries` 先不動） | 完成 |
| B3-2 | 問答的轉向量、生成答案：重試、總時間的控制、用量改成回傳值（拿掉 callback） | 完成（`_with_retries` 之後沒有呼叫者，B3-3 拿掉） |
| B3-3 | 拿掉沒人用的重試 helper、錯誤分類和告警一起檢查（S3 client、CloudWatch 的規則、部署腳本、測試） | 還沒開始 |
| B4 | probe、計時的 log、文件 | 還沒開始 |

全專案的可讀性整理（A2～A6：問答服務、前端、eval、train、零碎的部分）先做完 B 再做，不取消。

## 代價

- OpenAI 停擺幾分鐘這類暫時故障時，期間上傳的文件要使用者一份一份按重試；以前系統會在約 10 分鐘內自己再試。005 當時考慮過、沒選這個做法，現在選它，換來程式少掉一整條跨層的流程。
- 心跳改成每批一次之後，worker 當掉要等最後一次報平安後 10 分鐘才會顯示「處理中斷」（原本約 5 分鐘）。之後也不會有別的 worker 自動接手重做，要使用者按重試。
- 取消拿掉之後，不想等的文件只能刪掉。以前的取消也不會省到已經花掉的錢。處理中只顯示「處理中」，看不到轉到第幾段。
- 文件處理的轉向量，暫時性錯誤從一共試 5 次變成 3 次；OpenAI 叫我們等的時候最多會照等 120 秒（原本 60 秒），超過 120 秒就直接失敗、不等了。
- 問答遇到網路瞬斷會直接回 503，使用者要再問一次。
- 部分取代 005、007、008、009 的決定；那幾份的背景和當時的考量照舊保留。
