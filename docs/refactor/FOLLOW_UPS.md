# Cloud Core 重構：後續要驗收的事

重構過程中發現、還沒處理完或還沒驗證的事（docs/decisions/046）。處理完的在「狀態」寫明是哪個階段、怎麼驗證的，不刪掉，留著當紀錄。

## 程式

| 項目 | 為什麼要注意 | 狀態 |
|---|---|---|
| 處理到一半文件被刪掉時，`_stop_after_losing_claim()` 的 `db.refresh(document)` 會失敗 | 文件已經不在了，refresh 讀不到會丟出錯誤：worker 被當成當掉（寫 ERROR、工單被 SQS 重送），本機模式上傳的請求回 500 | 待處理（B2-2） |
| 記用量失敗時，OpenAI 的費用已經花了但沒記到 | 每日上限會少算這一批。要確認：worker 不會繼續轉下一批（不再花錢），而且留下告警看得到的錯誤紀錄 | 待確認（B2-2） |
| 刪除文件剛好碰上 worker 最後 commit 的那一瞬間，可能因為外鍵回 500 | 改之前就有的情況，機率很低；要修的話是 chunks 的外鍵加 `ondelete="CASCADE"`（要 migration） | 待決定 |
| 前端的進度、取消 | B2-1 之後進度不再更新（畫面只顯示「處理中」）；取消按鈕還在 | B2-3 |

## 雲端（部署之後才能驗證）

| 項目 | 為什麼要注意 | 狀態 |
|---|---|---|
| 心跳的期限 10 分鐘沒有在 AWS 上實測 | 390 秒是用每次嘗試的等待上限算出來的。等待上限是 httpx 每一次讀取的上限，不是整個請求的總時間：回應一直很慢地傳，一批還是可能更久。S3 在異常時，boto3 的等待上限加預設的重試，下載也可能更久。被誤判時存結果會被擋下來，資料不會錯，但會白做一次、顯示「處理中斷」 | 部署後量：一份大文件從取得租約到每次報平安的間隔（log 的 claimed、chunked、openai_usage 的時間差） |
| worker 的 `sqs:ChangeMessageVisibility` 權限 | B1 之後用不到了。要先部署新程式、確認沒問題，再收回權限 | 部署後 |
| Lambda 處理到一半被中斷 | 改成 10 分鐘沒報平安才標中斷，原本的演練 3 是 5 分鐘 | 部署後重做演練 3 |
